## 1. Обзор

CH32V003 не имеет аппаратного EEPROM. Данные эмулируются в последних 256 байтах flash (16 КБ чипа) с использованием алгоритма **линейного EEPROM** — данные записываются последовательно в слоты; при заполнении всех слотов стираются все flash-страницы и цикл повторяется.

**Ключевые характеристики:**
- Flash чип: 16 КБ (0x08000000 .. 0x08003FFF)
- EEPROM-область: 256 байт (0x08003F00 .. 0x08003FFF) = 4 страницы × 64 байта
- Размер структуры: 32 байта (ровно 8 flash-слов)
- Слотов: 8 (256 / 32 = 8)
- Целостность данных: каждая запись содержит CRC32 + номер последовательности + версию
- Стирание: постраничное (только при записи в первый слот страницы)
- CRC: nibble-based таблица (16 записей, компактно и быстро)
- Защита flash: BSY check + отключение прерываний при записи/стирании

## 2. Структура `ee_data`

### 2.1. Layout (32 байта)

```
Смещение Размер Поле               Описание
-------- ------ ----               --------
  0        4    seq                Номер последовательности (определяет актуальную запись)
  4        1    version            Версия структуры (совместимость прошивок)
                                   WARNING: packed uint8_t баг — использовать raw bytes
  5        2    defauil_ui1        UI по умолчанию (часть 1)
  7        1    uif                UI флаги (packed bitfield)
  8        1    aux                Флаги подсветки/маяка (packed bitfield)
  9        3    eng                Инженерные флаги (packed bitfield)
 12        1    usr                Пользовательские флаги (packed bitfield)
 13        1    defauil_ui2        UI по умолчанию (часть 2)
 14        1    defauil_ui3        UI по умолчанию (часть 3)
 15       10    slots[10]          Массив слотов данных
 25        3    reserved           Добивка для поддержания размера 32 байта
 28        4    crc                CRC32 предыдущих 28 байт (seq..reserved)
-------- ----
Итого:   32 байта
```

### 2.2. Битовые флаги

```c
// aux_flags (1 байт, смещение 8)
bcklight_type  : 1   // Тип подсветки (0 или 1)
bcklight_color : 1   // Цвет подсветки (0 или 1)
beacon_on      : 1   // Маяк вкл/выкл (0=выкл, 1=вкл)
beacon_mode    : 2   // Режим маяка (0..3)
beacon_type    : 3   // Тип маяка (0..7)

// eng_flags (3 байта, смещение 9)
min_level : 5         // Минимальный уровень (0..31)
vc        : 7         // Коррекция напряжения (-64..+63)
tc        : 7         // Коррекция температуры (-64..+63)
reserved  : 5         // Зарезервировано

// usr_flags (1 байт, смещение 12)
t_calibr   : 4        // Калибровка температуры (0..15)
eaux_onoff : 1        // Доп. экран вкл/выкл
id_plus_sid: 1        // Режим ID + SID
reserved   : 2        // Зарезервировано

// ui_flags (1 байт, смещение 7)
ui_index   : 2        // Индекс интерфейса (0..3)
off_bckl   : 1        // Подсветка выключена
use_memory : 1        // Использовать память
reserved   : 4        // Зарезервировано
```

## 3. Требования к структуре

### 3.1. Размер должен быть кратен 4 (КРИТИЧНО)

```c
sizeof(struct ee_data) ОБЯЗАН быть кратным 4 (DATAWIDTH)
```

**Почему:**
- Запись/чтение идёт через `FLASH_ProgramWord()` — побайтово по 4 байта
- Цикл записи: `for (i = 0; i < sizeof / 4; i++)` — записывает `sizeof/4` слов
- Если sizeof не кратен 4 — последний байт CRC не попадает во flash
- При следующем чтении `temp.crc` получает мусор в старшем байте → CRC всегда падает

**Как обеспечить:**
- Все поля суммируются до кратного 4 числа
- Если не хватает — добавить `uint8_t reserved[N]` для добивки
- Проверить: `4+1+2+1+1+3+1+1+1+10+3+4 = 32` ✓

### 3.2. Атрибуты компилятора

```c
struct __attribute__((packed, aligned(4))) ee_data { ... };
```

- `packed` — убрать padding между полями (иначе компилятор вставит выравнивающие байты)
- `aligned(4)` — выровнять структуру по 4 байтам в памяти (нужно для работы с flash-словами)

### 3.3. Порядок полей

Поля **обязаны** идти в том порядке, в котором они записываются во flash. CRC вычисляется по полям `seq` .. `reserved` (28 байт) и сохраняется в `crc` (последние 4 байта).

Порядок полей определяет:
- Какие байты входят в CRC
- Как данные распределяются по flash-словам
- Совместимость при обновлении прошивки

## 4. Расположение во Flash

### 4.1. Карта памяти

```
0x08000000 ┌─────────────────────────────┐
           │                             │
           │     Программа (16000 байт)  │
           │                             │
0x08003EFF ├─────────────────────────────┤
0x08003F00 │  Слот 0 (32 байта)         │  ← Страница 1 (64 байта)
0x08003F20 │  Слот 1 (32 байта)         │
0x08003F40 │  Слот 2 (32 байта)         │  ← Страница 2 (64 байта)
0x08003F60 │  Слот 3 (32 байта)         │
0x08003F80 │  Слот 4 (32 байта)         │  ← Страница 3 (64 байта)
0x08003FA0 │  Слот 5 (32 байта)         │
0x08003FC0 │  Слот 6 (32 байта)         │  ← Страница 4 (64 байта)
0x08003FE0 │  Слот 7 (32 байта)         │
0x08003FFF └─────────────────────────────┘
```

### 4.2. Страницы flash

| Страница | Адрес начала | Адрес конца | Слоты |
|----------|-------------|-------------|-------|
| 1        | 0x08003F00  | 0x08003F3F  | 0, 1  |
| 2        | 0x08003F40  | 0x08003F7F  | 2, 3  |
| 3        | 0x08003F80  | 0x08003FBF  | 4, 5  |
| 4        | 0x08003FC0  | 0x08003FFF  | 6, 7  |

- Размер страницы CH32V003: **64 байта**
- EEPROM-область: **256 байт** (4 страницы)
- Слотов: **8** (256 / 32 = 8)

### 4.3. Стирание

Flash на CH32V003 стирается **страницами** (64 байта). Два сценария:

**A. Постраничное стирание (обычная работа):**
При записи в ПЕРВЫЙ слот страницы (адрес кратен размеру страницы):
1. Проверяем, стёрта ли страница (`is_page_erased`)
2. Если не стёрта — стираем только эту страницу
3. Другие страницы остаются нетронутыми (данные сохранены)

**B. Полное стирание (все слоты заняты):**
Когда заполнены все 8 слотов:
1. Стираются все 4 страницы последовательно
2. Запись продолжается с начала (слот 0)

**Почему постраничное:**
- Уменьшается износ flash (стираем 64 байта вместо 256)
- Лучшая безопасность при потере питания (затронута только 1 страница)
- Другие страницы служат бэкапом до перезаписи

## 5. Алгоритм работы

### 5.1. Инициализация (первый запуск)

```
flash пуста → read_ee() возвращает 0
             → init_ee() заполняет ee defaults
             → version = EE_VERSION
             → seq = 0
```

### 5.2. Запись (каждый RESET)

```
┌─────────────────────────────────────────────────────┐
│ 1. read_ee() — ищем последнюю валидную запись       │
│    flash_search_address() сканирует слоты 0..7       │
│    → ResAddress = адрес первого свободного слота     │
│    → MaxSeq = максимальный seq среди записей         │
├─────────────────────────────────────────────────────┤
│ 2. Если flash пуста → init_ee() (defaults)           │
├─────────────────────────────────────────────────────┤
│ 3. write_ee() — сохраняем:                          │
│    a. ee.seq = MaxSeq + 1                           │
│    b. ee.crc = CRC32(seq..reserved)                 │
│    c. Используем ResAddress из read_ee (без re-scan)│
│    d. Если ResAddress == 0 → повторный поиск/стирание│
│    e. Если первый слот страницы → стираем страницу   │
│    f. __disable_irq()                               │
│    g. FLASH_ProgramWord() × 8 слов (32 байта)       │
│    h. flash_wait_bsy() + FLASH_Lock()               │
│    i. __enable_irq()                                │
└─────────────────────────────────────────────────────┘
```

### 5.3. Чтение (read_ee)

```
flash_search_address() → находит последний валидный слот
    ↓
Копируем из flash в RAM
    ↓
CRC32(вся структура включая crc) == 0?
    ├── Нет → данные повреждены, возвращаем ошибку
    └── Да ↓
version == EE_VERSION?
    ├── Нет → несовместимость прошивок, возвращаем ошибку
    └── Да → копируем в ee, возвращаем успех
```

### 5.4. Поиск слотов (flash_search_address)

```
current = PAGE_WRITE_START_ADDR (0x08003F00)

┌─► current <= PAGE_WRITE_END_ADDR - 32 ?
│       ├── Да ─► is_slot_valid(current)?
│       │           ├── Да ─► читаем seq, обновляем MaxSeq
│       │           │         current += 32 → следующий слот
│       │           └── Нет → write_addr = current (свободен)
│       │                     break → возвращаем write_addr
│       └── Нет → все слоты заняты, возвращаем 0
└─────────────────────────────────────────────────┘
```

### 5.5. Проверка валидности слота (is_slot_valid)

```
Первый байт == 0xFF?  ──► Да → слот пуст (стиранная flash)
         │
         Нет
         ↓
Копируем 32 байта из flash
         ↓
CRC32(первые 28 байт) == temp.crc?
         ├── Да → слот валиден ✓
         └── Нет → данные повреждены ✗
```

### 5.6. Стирание (erase_flash_page)

```
__disable_irq()
Unlock flash
flash_wait_bsy()
Очистить флаги ошибок
Стереть страницу (64 байта)
flash_wait_bsy()
Lock flash
__enable_irq()
```

## 6. Поле version

### 6.1. Назначение

Поле `version` (1 байт по смещению 4) защищает от несовместимости прошивок. При изменении layout структуры между версиями прошивки version инкрементируется. Старые записи с другой версией автоматически отвергаются.

### 6.2. Обход бага компилятора

**GCC для CH32V003 имеет баг:** чтение `uint8_t` поля из `packed` структуры возвращает 0 вместо реального значения. Это влияет на поле `version`.

**Решение:** обращаться к version через raw byte pointer вместо struct field:

```c
// Запись version:
uint8_t *ee_raw = (uint8_t*)(void*)&ee;
ee_raw[sizeof(uint32_t)] = EE_VERSION;  // смещение 4

// Чтение version:
uint8_t *raw_bytes = (uint8_t*)(void*)&temp_ee;
uint8_t file_version = raw_bytes[sizeof(uint32_t)];  // смещение 4
if (file_version != EE_VERSION) { ... }
```

**Почему смещение 4:** `version` расположен после `seq` (uint32_t, 4 байта) для обеспечения word-alignment первого flash-слова.

### 6.3. Когда инкрементировать

Инкрементировать `EE_VERSION` при:

| Изменение | Инкремент? | Причина |
|-----------|-----------|---------|
| Добавить/удалить поле | Да | Layout изменён, старые данные интерпретируются неправильно |
| Переставить поля | Да | CRC вычисляется по другим байтам |
| Изменить размер поля | Да | Layout изменён |
| Изменить default значения | Нет | Layout не изменился |
| Переименовать поле | Нет | Layout не изменился |
| Изменить bitfield layout | Да | Байтовое представление изменилось |

### 6.4. Стратегия миграции

При инкременте version старые данные **автоматически отвергаются** (считаются пустыми → `init_ee` загружает defaults). Это безопасно, потому что:

1. Проверка CRC проходит (данные целостны)
2. Проверка version падает → `read_ee` возвращает 0
3. `init_ee` загружает свежие defaults
4. Пользовательские настройки теряются, но устройство работает

**Для критичных данных, которые должны пережить обновление:**

```c
// Вариант 1: Добавить код миграции
int read_ee(void) {
    // ... проверка CRC ...
    if (temp_ee.version == 1) {
        // Миграция v1 → v2
        migrate_v1_to_v2(&temp_ee);
    } else if (temp_ee.version == EE_VERSION) {
        // Текущая версия — миграция не нужна
    } else {
        return 0;  // Неизвестная версия
    }
    memcpy(&ee, &temp_ee, sizeof(ee));
    return 1;
}

// Вариант 2: Сохранить обратную совместимость
// Не менять layout — добавлять новые поля только в конец
// Старая прошивка игнорирует новые поля (они в reserved)
```

## 7. Безопасность при потере питания

### 7.1. Потеря питания во время стирания одной страницы

**Сценарий:** стирание одной страницы завершено, новая запись не началась.

**Результат:**
- Одна страница стёрта (0xFF)
- Другие 3 страницы нетронуты (данные сохранены)
- При следующем boot: `flash_search_address` продолжает с нетронутых данных
- Слоты стёртой страницы считаются пустыми → пропускаются

**Вердикт:** Безопасно — потеряны только данные стёртой страницы, другие сохранены.

### 7.2. Потеря питания во время полного стирания (все слоты заняты)

**Сценарий:** 2 из 4 страниц стёрты, потеря питания.

**Результат:**
- Часть страниц стёрта, часть нетронута
- При следующем boot: валидные слоты на нетронутых страницах используются
- Стёртые страницы пропускаются

**Вердикт:** Частичная потеря данных — но предыдущие записи на нетронутых страницах выживают.

### 7.3. Потеря питания во время записи (пословно)

**Сценарий:** 3 из 8 слов записаны, потеря питания.

**Результат:**
- Слот содержит частичные данные + 0xFF (незаписанные)
- Проверка CRC падает → слот считается невалидным
- При следующем boot: слот пропускается, используется предыдущая валидная запись

**Вердикт:** Безопасно — старые данные сохранены.

### 7.4. Потеря питания между read_ee и write_ee

**Сценарий:** данные прочитаны, потеря питания до записи.

**Результат:**
- Flash не изменена (записи не было)
- При следующем boot: читаем те же данные

**Вердикт:** Безопасно — нет потери данных.

### 7.5. Сводка

| Сценарий | Потеря данных? | Восстановление |
|----------|---------------|----------------|
| Во время стирания 1 страницы | Только 1 страница | Другие страницы целы |
| Во время полного стирания | До 2 страниц | Другие страницы целы |
| Во время записи | Текущая запись | Предыдущая запись сохранена |
| Между read/write | Нет | Та же запись |

## 8. Расширение хранилища

### 8.1. Текущая конфигурация (256 байт)

Уже настроена EEPROM на 256 байт (4 страницы, 8 слотов).

### 8.2. Уменьшение до 128 байт (2 страницы, 4 слота)

Если критично место под программу:

```c
// Изменить начальный адрес обратно на 128-байтную область
#define PAGE_WRITE_START_ADDR  ((uint32_t)0x08003F80)  // Было 0x08003F00
```

В `platformio.ini`:
```ini
build_flags =
    -Wl,--defsym=FLASH_SIZE=16256    ; 16384 - 128 = 16256
```

### 8.3. Увеличение размера структуры

Добавить новые поля, сохранив кратность 4:

```c
struct __attribute__((packed, aligned(4))) ee_data {
    uint32_t seq;               // 4 байта (word-aligned)
    uint8_t version;            // 1 байт (использовать raw bytes)
    // ... существующие поля ...
    uint8_t new_field1;          // +1 байт
    uint8_t new_field2;          // +1 байт
    // Скорректировать reserved для поддержания кратности 4
    uint32_t crc;                // 4 байта
};
```

**Последствия:**
- Слотов на 256-байтную область: 256 / sizeof(struct) = меньше слотов
- CRC вычисляется по (sizeof - 4) байтам
- Уменьшается износостойкость (меньше слотов → чаще стирание)
- **Не забудьте инкрементировать EE_VERSION**

## 9. Чеклист модификации

### Перед изменением структуры

- [ ] `sizeof(struct ee_data)` кратен 4?
- [ ] CRC вычисляется по всем полям ДО `crc`?
- [ ] Поля идут в порядке записи (порядок в памяти = порядок в коде)?
- [ ] `packed` и `aligned(4)` стоят?
- [ ] Количество слотов пересчитано?
- [ ] `EE_VERSION` инкрементирован?
- [ ] Старые данные совместимы? (если нет → нужна миграция)
- [ ] **Новые `uint8_t` поля?** Использовать raw bytes (packed uint8_t баг)

### Типичные ошибки «Storage is EMPTY»

1. **sizeof не кратен 4** — CRC не записывается/читается полностью
2. **Нет `packed`** — компилятор вставляет padding, реальный размер больше ожидаемого
3. **Поля переставлены** — CRC вычисляется по другим байтам
4. **`reserved` не там** — ломает выравнивание и размер
5. **Packed `uint8_t` поле** — читается как 0 в CH32V003 GCC (использовать raw bytes)

### Как добавить новое поле

1. Определить размер поля (1, 2 или 4 байта)
2. Добавить после последнего поля, перед `reserved` или `crc`
3. Скорректировать `reserved` для поддержания размера 32 байта (или расширить структуру)
4. Проверить, что `sizeof` кратен 4
5. Инкрементировать `EE_VERSION`
6. Обновить `init_ee()` — задать значение по умолчанию
7. Обновить `wl_flash.h` — добавить комментарий с offset/size
8. Если старые данные должны пережить — добавить код миграции в `read_ee()`
9. **Если поле `uint8_t`** — обращаться через `((uint8_t*)&struct)[offset]`
